## 0. 已确认的决策

以下内容已由项目所有者确认，后续实施以此为准。

### 0.0 已确认的既有设计（不修改）

| 设计 | 确认内容 | 对方案的影响 |
|---|---|---|
| 计数器 | 工作正常。每日指标允许多行，读取端（`metrics_excel.py`）按日期合并求和；同日多行、含 0 值行都属于设计内行为 | 撤销“计数器损坏”结论；阶段 0 只做观测增强与读取口径核对，不改计数逻辑 |
| `BOT_NAME` 硬编码 | 故意设计。用于识别“是否在叫自己”（@ 判断、CQ 码清洗、回复对象） | 撤销“改为配置项”的建议；保留名字锚点 |

### 0.1 笔记字数上限与满了的策略

采用“拒绝写入”，不做 FIFO 自动淘汰。

| 配置项 | 建议默认值 | 说明 |
|---|---:|---|
| `note_entry_max_chars` | 200 | 单条笔记字符上限 |
| `note_file_max_chars` | 8000 | 单个笔记文件字符上限 |
| `note_max_lines` | 100 | 单个笔记文件条目上限 |
| `note_read_max_chars` | 2000 | 单次读回上限 |
| `note_brief_max_chars` | 400 | 动作层摘要总长 |
| `note_brief_recent_lines` | 5 | 动作层摘要每本最近条目数 |

- 写入前同时检查字符数与 UTF-8 字节数。
- 单条超长：在句末标点处截断，返回 `truncated=True` 并在行为记忆中留痕。
- 文件已满：返回明确错误“笔记已满，请先划掉旧条目”，不再静默返回 `None`。
- 修改必须唯一命中；多命中时拒绝并返回候选行，模型改用更长 `old_text` 或 `line`。
- 删除改为独立动作 `delete_txt`，不再用“省略 `new_text`”隐式删除。
- 所有写/改/删操作写 `data/test/note_audit.jsonl` 审计日志（时间、文件、旧文本、新文本、来源）。

### 0.2 收藏提示后置

“我收藏了……”这条**记忆**直接追加在被收藏图片的描述之后；用户侧不可感知。

具体语义：

1. 收到媒体时，`register_pending()` 的记录里增加 `memory_ids`，保存该媒体描述对应的记忆 ID。
2. 动作层决定收藏后：
   - 生成 `我收藏了{一张图/一个表情包}，内容是：{desc}` 记忆；
   - 使用与被收藏媒体相同的时钟时间戳；
   - 立即 `add_link(media_mem_id, favorite_mem_id, 1.0, "causal")`，保证在记忆图和事件段里紧邻原图；
   - 对话历史中把这条记录追加在“（发送了图片/表情包，内容是…）”之后，而不是单独占一条用户可见消息；
   - **不向群里发送任何“已收藏”提示**，也不在面板对话流里伪造一条用户可见消息。
3. 动作层提示词中，“收藏”选项放在【本轮收到的媒体】之后，确保模型先看到图片描述，再看到“如果想留下，用 save_image/save_sticker 引用上面的编号”。

说明：发送类动作（`image` / `sticker`）的“我发了……”记忆仍按现有方式记录，用户同样不可见；它与 0.2 是两件事，不要混淆。

### 0.3 @ 功能

允许模型“自主 @ 别人”，但**不新增、不修改 LLM 返回字段**；原则是不增加 LLM 的思考复杂度，能降则降。

采用“输出后处理”方案：

1. `verbalize` 的 JSON 结构保持 `{"say": bool, "text": str}` 不变。
2. 模型在 `text` 里自然写出 `@张三` 时，发送前由确定性后处理把 `@名字` 转成 OneBot `at` 消息段：
   - 名字必须命中 `config/qq_manifest.json` 的 `name_mapping`（群内昵称或映射名）；
   - 未命中则保留原文，不猜测 QQ 号；
   - 忽略邮箱、URL、代码块里的 `@`。
3. 只有“ incoming 消息直接 @ 了机器人”时，才默认 @ 回触发者；普通群消息、主动发言、发图/表情包不强制 @。
4. 不在提示词里增加“你可以 @ 别人”的指令，也不增加 `at` 字段。这样模型仍只做它本来就在做的事，复杂度不升反降。
5. `send_group_msg()` 增加 `at_qq`、`reply_msg_id` 参数，用结构化消息段发送；非法/机器人自己/`all` 一律剥离。

### 0.4 memory.json 的去留

可以删去，但启动时必须先尝试从 `memory.json` 恢复数据，再删除；没有 `memory.json` 时才从 SQLite 恢复。

安全迁移顺序（两阶段删除）：

1. 启动时若 `data/test/memory.json` 存在：
   - 读取并校验 JSON；
   - 把其中 `memories` 逐条 `INSERT OR IGNORE`/`REPLACE` 进 SQLite（以 JSON 为准补齐 SQLite 缺失项）；
   - 把 `links` 逐条写入 SQLite `links` 表；
   - `wordweb` 单独落到 `data/test/wordweb.json`（见下方说明）；
   - 提交事务并 `fsync`；
   - 成功后把 `memory.json` 重命名为 `memory.json.migrated.bak`，而不是直接 `remove`；
   - 下一次启动若看到该 `.bak` 且迁移标记存在，再删除它。
2. 若 `memory.json` 不存在：
   - 走现有 `_restore_hot_memories_from_db()`，按 rowid 倒序取 TOP-N 热记忆；
   - 链接走 `_restore_links_from_db()`。
3. 迁移完成后：
   - `save_all_data()` 不再写 `memory.json`；
   - 新增 `data/test/memory_json_migrated.flag` 记录迁移完成；
   - 工具 `fix_memory_time.py` 中对 `memory.json` 的更新逻辑改为可选的遗留兼容分支。

**wordweb 不能丢**：当前 `wordweb` 只存在 `memory.json` 里，SQLite 没有对应表。删除 `memory.json` 前必须二选一：

- 方案 A（推荐）：新建 `data/test/wordweb.json` 专门存字词网络，`save_all_data()` 只写这个较小的文件；
- 方案 B：给 SQLite 建 `wordweb` 表，写入与恢复都走表。

在方案落地前，不得直接删除 `memory.json`，否则会丢失字词共现网络。

## 1. 阶段 0 核查结果

### 1.1 计数器核查结果

**结论：按当前设计正常工作，不列为待修复项。**

核查依据：

- `utils/persistence.py:84-87` 在每次保存时把内存计数器导出到 `data/test/metrics_counters.json`。
- `core/memory_engine.py:103-144` 的 `_write_daily_metrics()` 在睡眠维护时把“当前累计值 − 上次基线”追加到 `data/test/metrics_daily.jsonl`。
- `metrics_excel.py:62-91` 读取日志时**按日期合并同日记录并求和**，因此同一天出现多行、甚至出现 0 值行，都属于设计内行为，不是重复写坏。
- 当前日志 52 行 / 21 个日期，`mem_created`、`link_created`、`wordweb_created`、`msg_sent`、`self_ref` 均有非零增量，说明主链路计数在走。
- 启动时 `load_all_data()` 先导入 counters 快照，`_init_metrics_counters()` 再从基线初始化；两者最终服务于“累计值 + 每日基线”的同一套口径，读取端合并后结果一致。

因此原方案中的“启动顺序覆盖、写入非原子、每日多行、删除漏计”等条目**全部撤销**，不作为阶段 0 的修复内容。

仅保留两个**口径确认项**，不影响计数器的正常使用，只在需要精确统计时再处理：

1. `active_attempt` / `active_success` 目前没有任何递增点。若“主动发言”指标已不再需要，可从 `_export_metrics_counters()`、`_init_metrics_counters()` 和 `metrics_excel.py` 的 `FIELD_TITLES` 中一并移除；若仍需要，再接到实际的主动发言尝试/成功路径上。
2. `link_deleted` 目前只统计睡眠维护的两条剪枝路径，`decay_link()` 低于阈值时的即时删除不计入。若“链接删除”只指睡眠维护的批量清理，这是正确口径；若要统计所有删除，再补计。

阶段 0 对计数器的动作只剩两项：

- 增加观测字段（LLM 调用次数/耗时/token、事件循环阻塞、锁等待、下沉耗时等），不改现有计数逻辑；
- 增加一个**只读**核对脚本（`tools/metrics_verify.py`，不命名为 `test_*.py`），验证“按日期合并后的总量”与 counters/baseline 的关系、确认文件可解析且无非负异常。它只读文件，不修数据。

**验收**：

- 用 `metrics_excel.py` 或核对脚本读取现有日志，合并结果一致、可解析；
- 新增 1 条记忆、1 条链接、1 条消息后，对应计数在下次保存/每日写入时体现；
- 不改变同日多行的既有写入行为。

### 1.2 全项目读写冲突审计

**结论：当前不是“单写者”架构，存在跨线程与跨进程两类冲突。**

#### 数据文件所有权现状

| 文件 | 当前写入方 | 当前读取方 | 风险 |
|---|---|---|---|
| `data/test/memory.db` | `memory_engine` 连接、`concept_store` 连接 | 同左 + 外部工具 | 两个 SQLite 连接并发写，无 `busy_timeout`，可能 `database is locked` |
| `data/test/memory.json` | `save_all_data()` | `load_all_data()`、`fix_memory_time.py` | 36MB 级整文件 dump，锁内 I/O，且与外部工具可并发 |
| `data/test/faiss.index` / `faiss_mapping.json` | `save_all_data()` | `load_all_data()` | 写盘期间主线程持 `_data_lock`；外部工具可并发 |
| `data/test/message_state.json` | QQ 服务线程、面板 `fake_*` | 同左 | 原子写但多线程/多进程会互相覆盖 |
| `data/test/dialogue_state.json` | QQ 服务、CLI、面板 | 同左 | `save_state()` 非原子 `open('w')` |
| `data/test/clock_state.txt` | 所有调用 `clock.save_state()` 的路径 | 启动加载 | 非原子写，崩溃可能半截 |
| `data/test/biorhythm.json` | 生物钟 `save()` | 启动加载 | 原子写，但无跨进程锁 |
| `data/test/assets/index.json` | 动作层 | 动作层 | 原子写，但外部工具可并发 |
| `data/notes/*.txt` | 动作层 | 动作层 | 读-改-写无按文件锁 |
| `data/test/metrics_*.json/jsonl` | `save_all_data()`、`sleep_cleanup()` | `metrics_excel.py` | 读取端按日期合并，结果正常；并发读写在窄窗口内，低风险 |
| `config/api_config.json` | 面板 | QQ 服务热重载、所有模块 | 面板非原子写；服务读到时可能拿到半截 JSON |

#### 确定的冲突点

1. **锁内做 I/O**：`utils/persistence.py:50-94` 在 `_data_lock` 内 dump 36MB JSON、写 faiss、同步 SQLite；`core/memory_engine.py:321-354`、`397-429` 在 `_data_lock` 内 `executemany + commit`。
2. **无锁突变全局字典**：`_load_memory_from_db()`、`_batch_load_memories()`（`core/memory_engine.py:289-319`）直接写 `memories` / `hot_ids`，而调用它们的 `retrieve_similar()` 并不持锁。
3. **无锁遍历**：`semantic_dedup()`（`core/memory_engine.py:1095`）直接遍历 `memories.items()`。
4. **重建索引长锁**：`_rebuild_faiss_index()`（`core/memory_engine.py:671-685`）在 `_data_lock` 内全表读 + 重建，睡眠维护还同时持有 `_io_lock`。
5. **两个 SQLite 连接**：`core/memory_engine.py:217` 与 `core/concept_store.py:77` 各自 `sqlite3.connect(..., check_same_thread=False)`，都没有 `busy_timeout`。
6. **多入口无进程锁**：只有面板走 `run/control_panel.lock`；`main.py`、直接运行 `qq_bot.py`、`manager.py` 都不加锁。`fix_memory_time.py` 会加面板锁，但加 `--force` 可绕过。
7. **配置写读竞争**：`panel_runtime.py:657-658` 用 `open('w')` 直接覆盖 `config/api_config.json`；运行中的 QQ 服务会热重载读取同一个文件。
8. **消息历史多写者**：`utils/message_history.py:126-162` 虽然是原子写，但每个进程各有一份内存 `_message_history`；面板 `fake_send/fake_think` 与 QQ 服务线程同时写会互相覆盖。
9. **指标读取与写入的时序**（低优先级）：`metrics_excel.py` 可能在写盘过程中读取；由于按行追加且按日期合并，一般不影响结果，但建议在阶段 4 统一为单写者并加文件锁。

#### 目标规则（阶段 4 落地）

1. **一个文件只有一个写者**：
   - `memory.db`：MemoryWriter（单线程或单进程）；
   - `faiss.index` / `faiss_mapping.json`：MemoryWriter；
   - `wordweb.json`：MemoryWriter；
   - `message_state.json`：QQ 服务单线程；
   - `dialogue_state.json`、`clock_state.txt`、`biorhythm.json`：Runtime 单写者；
   - `assets/index.json`、`notes/*.txt`：动作层单写者；
   - `metrics_*`：MetricsWriter；
   - `config/api_config.json`：面板单写者。
2. **读侧不持写锁**：读路径拿只读快照或短锁读取；不得在 `_data_lock` 内做 SQLite/文件 I/O。
3. **所有 JSON 原子写**：统一 `atomic_write_json(path, data)`（tmp + fsync + `os.replace` + Windows 权限重试）。
4. **所有 SQLite 连接**：`PRAGMA journal_mode=WAL`、`PRAGMA synchronous=NORMAL`、`PRAGMA busy_timeout=5000`；写事务串行。
5. **全局运行锁**：`run/runtime.lock` 由“拥有数据写权的进程”持有；`main.py`、`qq_bot.py`、`manager.py`、`fix_memory_time.py`、面板都先取锁；工具需要并发时显式 `--force` 并打印警告。
6. **进程内锁顺序固定**：`_io_lock → _data_lock`，任何新代码不得反向获取。
7. **跨进程消息历史**：只允许 QQ 服务写；面板的伪造发送/思考改为通过 Runtime 转发，不直接写文件。

## 2. 分阶段修复方案

### 阶段 0：基线观测（不修改现有计数逻辑）

**目标**：让后续所有优化都有可信的前后对比；计数器本身按既有口径使用，只补观测与只读核对。

任务：

1. 增加调用计数与耗时：

### 阶段 3：睡眠状态机与睡前/醒后提示

落点：`core/biorhythm.py`、`qq_bot.py:227-342`、`core/cognition.py:740-750,953-995`、新增 `core/sleep_coordinator.py`。

#### 3A. 单一状态源，修掉“醒后发不出去”

- `is_sleeping()` 改为以 `BIORHYTHM.is_asleep()` 为权威；`_sleeping` 只作为派生镜像，由状态转换回调更新，不再参与 OR 判断。
- 状态转换只由 `SleepCoordinator` 处理；`drift_loop` 和 `cognitive_loop` 只负责 tick。
- 认知循环观察到醒来时立即调用 `SleepCoordinator.on_wake()`，不再等 `drift_loop` 下一轮（最多 30 秒）。

#### 3B. 四态状态机

| 状态 | 认知循环 | 发送 | 提示 | 维护 |
|---|---|---|---|---|
| AWAKE | 正常 | 允许 | 普通 | 定时 |
| WIND_DOWN | 完成当前轮，不再开新动作 | 允许最后一次 | `pre_sleep` 一次 | 准备 |
| ASLEEP | 挂起 | 禁止（@ 唤醒除外） | 无 | 睡眠维护一次 |
| WAKING | 等待用户上下文或首轮 | 允许 | `post_wake` 一次 | 无 |

- **WIND_DOWN 进入条件**：`sleep_drive >= ONSET_THRESHOLD - pre_sleep_margin` 且已安静足够久。
- 给生物钟加 `sleep_hold_until`，wind-down 期间 `_maybe_sleep()` 不立即入睡，保证最后一轮能发送。
- **睡前提示**：`pre_sleep_text()` 只在本次入睡前注入一次；作为 `body_state` 传给 `verbalize`，不写成记忆；是否说“晚安”由 LLM 的 `say` 决定，不硬编码台词。
- **进入 ASLEEP**：清空 `current_keywords`、`_keyword_queue`、`prev_thought_text`、上一轮发言标志、反刍抑制计数。
- **醒来**：
  - `WAKING` 注入 `post_wake_text()`：包含“睡了多久”“自然醒/被叫醒”，只注入一次；
  - 被 @ 唤醒时等待该消息解析结果（或 2-3 秒 settle 窗口），让首轮围绕用户消息，而不是随机种子；
  - 自然醒允许首轮以新鲜随机种子开始，但不带入睡前 `prev_thought_text`。
- **提示呈现**：不继续作为普通记忆塞进 `pinned`；改为 `verbalize(..., body_state=...)` 独立字段。

#### 3C. 持久化补齐

- `Biorhythm.save()` 增加：`woke_by_user`、`last_feeling_time`、`last_guard_wake`、`_sleep_samples`、`_last_rhythm_sample`、`last_pre_sleep_time`、`wake_generation`。
- `load()` 对应恢复；兼容旧存档缺字段。
- 重启后若仍在 wake window 内，保留“刚醒/被叫醒”状态一次，不重复轰炸。

**验收**：

- 每次入睡前最多一条 `pre_sleep` 提示，最多一条 LLM 决定的“晚安”；
- 入睡瞬间不再出现“发送失败但仍记成我说”的记忆；
- 醒后第一条回复能立即发出，不再被 `_sleeping` 挡住；
- 醒后首轮不包含睡前关键词/睡前上一轮回复；
- `post_wake` 提示一觉只出现一次，重启不重复。

#### 4B. 独立写进程/线程

新增 `core/memory_writer.py`：

- 命令队列：`insert_memory`、`update_times`、`upsert_links`、`delete_links`、`delete_memories`、`snapshot`、`purge`、`rebuild_faiss`。
- 单写者，批量事务：攒 100ms 或 100 条命令，`BEGIN IMMEDIATE` → 执行 → `COMMIT`。
- `update_times` 按 `memory_id` 合并，只保留最新值。
- `create_memory` 等待 commit ack（保证不丢新记忆）；`touch` 不等待。
- 专用 SQLite 连接、`busy_timeout=5000`、WAL、`synchronous=NORMAL`。
- 队列有界：满时对 `create_memory` 背压，对 `touch` 合并/丢弃非关键更新。
- 原子写：
  - SQLite 用事务保证原子；
  - `wordweb.json` / faiss 用“临时文件 + fsync + `os.replace`”；
  - 写入顺序：先提交 SQLite（权威），再写派生文件；
  - 启动时用现有 `_faiss_snapshot_is_valid` 校验，不一致就重建。
- 模式开关 `memory_writer_mode=thread|process`：
  - 线程足够处理 SQLite I/O；
  - 若保留较大的派生文件序列化，用独立进程避免 GIL；
  - 进程模式用 `multiprocessing.Queue`，只传命令和紧凑数据，不传 768 维向量；子进程自己读 SQLite 生成快照。

#### 4C. 热记忆列表由另一条进程整理后替换回主进程

新增 `HotSetPlanner`：

- 输入：只含 `(id, last_accessed, half_life, last_strengthen_time)` 的紧凑快照，不传向量。
- 输出：`evict_ids` 列表（按 `last_accessed` 最旧优先）。
- 可运行在线程或独立进程；1500 条排序本身很便宜，进程化主要用于避免与主循环抢 GIL/调度。
- 主进程应用计划时做 **CAS 校验**：
  - 只淘汰 `last_accessed` 与快照一致、且 `last_strengthen_time` 未变化的条目；
  - 期间被访问过的条目跳过，下一轮重新评估；
  - 在短锁内更新 `memories/hot_ids`；
  - 发布新的只读快照（shallow copy + 版本号），读者拿引用即可。
- **原子替换语义**：主进程不是“把另一条进程的整个字典搬回来”，而是“接收淘汰计划 → 校验 → 本地应用 → 发布新快照”。这样既满足“另一条进程整理”，又不需要跨进程序列化大量向量。

**验收**：

- `_data_lock` 持有时间内不再有文件 I/O；
- 1500 热记忆 + 5000 热链接的下沉在主循环上 p99 停顿 < 50ms（写进程内部耗时可更长）；
- 下沉期间持续 `create_memory` / `access_memory`，不丢记忆、不误删刚访问的条目；
- kill -9 模拟写盘中断，重启后 SQLite 一致、快照被识别为无效并重建；
- 固定查询集的检索结果与改造前一致。

### 阶段 5：缓存命中优化与最终验收

#### 5A. LLM 缓存命中

落点：`core/llm_interface.py` 全部 prompt 构造处、`core/action_layer.py`。

改动：

1. 统一 prompt 布局：
   - 静态 system prompt 永远第一段且逐字节稳定；
   - 动态状态、时间、历史、记忆全部放到后面的 user 消息；
   - 不把 `datetime.now()`、随机候选顺序、随机对话窗口插进静态段。
2. 增加 `PromptSpec` / 哈希日志：
   - 记录静态前缀 SHA-256；
   - 确保 100 次调用不变；
   - 变更 prompt 时显式提升版本号。
3. 记录 usage：
   - `prompt_tokens`、`completion_tokens`、`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`（字段存在时）；
   - 接入面板指标。
4. 动作层候选顺序：
   - 保留“随机挑选”的产品意图，但把候选选定与 prompt 排序分开；
   - 同一轮/同一页内顺序稳定，翻页复用同一列表。
5. 可选 provider 缓存控制：
   - DeepSeek 类自动前缀缓存：无需 key，核心是稳定前缀；
   - 兼容 OpenAI 的接口如支持 `prompt_cache_key`，通过 `extra_body` 配置传入；
   - 不为了缓存把动态内容塞进 system prompt。
6. 只对无状态、确定性调用做响应缓存（图片描述）；`verbalize` / 动作决策 / 理解层不做响应缓存。

**验收**：

- 静态前缀哈希 100 次不变；
- 日志能看到 cache hit/miss tokens；
- prompt token 总量下降；
- 面板能显示缓存命中率。

#### 5B. 最终验收

- 功能回归：笔记限额/删改、纯媒体消息、复合消息、@ 回复、引用回复、睡眠前后、唤醒、反刍抑制、动作层发送。
- 性能回归：每条消息 LLM 次数、prompt token、事件循环 p99、`_data_lock` p99、保存/下沉耗时、启动时间。
- 数据安全：改造前备份 `data/test`；SQLite 迁移只增不减；快照损坏可回退；关停强制 flush。
- 长跑：24 小时 soak，重点看内存增长、热集是否稳定、日志是否有死锁/重复下沉、睡眠转换是否反复。
- 灰度开关：`memory_writer_mode`、`memory_json_migrated`、`action_spontaneous_prob`、`pre_sleep_margin`、`bot_name`、`cold_start_enabled`。

### 4.2 锁规则

1. 进程内：`_io_lock → _data_lock` 固定顺序；禁止反向。
2. 跨进程：`run/runtime.lock` 由数据写权拥有者持有；工具需显式 `--force`。
3. SQLite：`busy_timeout=5000`，写事务 `BEGIN IMMEDIATE`，不允许长事务。
4. 文件读：读到损坏 JSON 时重试一次；仍失败则使用上一份 `.bak`，并明确日志。
5. 任何新写路径必须说明：谁写、谁读、锁是什么、失败如何回退。

## 7. 建议执行顺序

```
阶段 0（观测 + 只读核对）
  ↓
阶段 1（笔记、图片描述、提示词弱化表演、动作层）
  ↓

  ↓

  ↓
阶段 4B/4C（MemoryWriter、HotSetPlanner）
  ↓
阶段 5（缓存命中 + 全量验收）
```

依赖关系：

- 阶段 2 的 ParseWorker 依赖阶段 0 的耗时观测，否则无法证明“事件循环不再被阻塞”。
- 阶段 3 依赖阶段 2 的关键词队列与消息上下文，否则醒后首轮仍可能被随机种子抢占。
- 阶段 4 依赖阶段 0 的锁等待指标，否则无法证明下沉不再卡主循环。
- 阶段 5 依赖阶段 1 的 prompt 瘦身，否则静态前缀再稳定，token 总量仍然偏高。
